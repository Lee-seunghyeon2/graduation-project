# v1 개선 후보 (v0 실사용 검증에서 발견)

v0는 "완성도 높은 최종 시스템"이 아니라 "핵심 아이디어가 동작하는 최소 버전"이 목표였고,
아래는 실제 LLM/실제 MCP 클라이언트로 검증하며 나온 관찰 중 v1에서 다룰 만한 항목이다.
(자세한 원본 트랜스크립트는 [v0-manual-verification.md](./v0-manual-verification.md) 참고)

## 1. degree 유형의 impact(high/low) 판단 보정 필요

**관찰**: "이 문장 조금만 더 자연스럽게 다듬어줘." 케이스에서 AmbiguityAnalyzer는 "조금만 더"를
`impact: low`로 판단해 SAFE_INFERENCE로 질문 없이 넘어갔다. 이는 스펙에 명시된 의도된 동작
("조금 더 자세히" 같은 표현으로 매번 질문하지 않는다)과 정확히 일치한다.

**남는 문제**: 이 판단은 문맥에 따라 달라져야 한다. 같은 "조금만 더"라도
"제출 마감 직전이라 절대 어색하면 안 된다" 같은 문맥이라면 impact가 high로 올라가야 맞는데,
현재 AmbiguityAnalyzer 프롬프트는 이런 맥락적 위험도까지 충분히 반영하는지 실증되지 않았다.

**제안**: DecisionEngine 규칙(RESOLVED/SAFE_INFERENCE/CLARIFICATION_REQUIRED 분기) 자체는
그대로 두고, AmbiguityAnalyzer 시스템 프롬프트에 "impact 판단 시 문맥의 긴급도/되돌리기 어려움
정도"를 더 명시적으로 고려하도록 지침을 보강. 마감/불가역성 관련 키워드가 섞인 실제 케이스를
모아 회귀 테스트로 추가.

## 2. omission/reference 유형에서 "문맥이 강해도 후보가 2개 이상"인 경우가 실제로 발생

**관찰**: 초기 수동 스크립트 테스트에서 "정리해줘." + 직전 대화("보고서 초안을 검토했는데 문단이
뒤죽박죽이야.")를 입력했을 때, 개발자가 손으로 짠 stub 테스트는 단일 해석(RESOLVED)을 가정했지만
실제 Gemini는 "문단 구조 재배치"와 "내용 요약·정돈"이라는 2개의 합리적 후보를 스스로 찾아내
`context_support: strong`임에도 `CLARIFICATION_REQUIRED`로 판단했다.

**해석**: DecisionEngine 규칙(후보 2개 이상 + impact high → 질문)은 스펙대로 정확히 동작한 것이고,
버그가 아니라 "실제 모델의 모호성 감지가 사람의 직관보다 더 보수적일 수 있다"는 실증 사례다.

**제안**: 이런 경우가 실제로 얼마나 자주 발생하는지, 그리고 이게 사용자 경험상 "적절한 신중함"인지
"과한 질문"인지 v1에서 실제 사용자 피드백/추가 케이스로 판단 필요. 필요하다면 omission 유형에 한해
"직전 대화가 방금 전 1턴 이내로 매우 가까우면 context_support를 strong으로 더 적극적으로 매길 것"
같은 프롬프트 보강 검토.

## 3. CLARIFICATION_REQUIRED가 3개 초과일 때의 정책 미정

**관찰**: `ClarificationQuestionGenerator`는 우선순위로 정렬해 상위 3개만 질문하고 나머지는
`decision: CLARIFICATION_REQUIRED`인 채로 `question_id` 없이 남는다. 이 항목들이 다음 턴에서
어떻게 처리되어야 하는지(다음 라운드에 자동으로 질문에 포함되는지 등) 아직 명확히 설계/테스트되지
않음.

**제안**: 4개 이상 동시에 걸리는 실제 케이스를 수집한 뒤, "이번 라운드에서 답변되지 않은
CLARIFICATION_REQUIRED 항목은 다음 `analyze_prompt` 호출에서 자동으로 이어서 질문한다"는 정책을
명시적으로 구현 + 테스트.

## 4. PromptBuilder는 템플릿 치환 방식 — 스펙 예시 수준의 자연스러운 재작성은 아님

**관찰**: 현재 `improved_prompt`는 "[명시화된 요청]" 안에서 모호 표현을 resolved_value로
문자열 치환하는 결정론적 템플릿이라, 스펙 7번 예시("AI 공모전 안내문을 분석하여...")처럼
한 문단으로 자연스럽게 재작성되지는 않는다. 실사용 검증에서 나온 `improved_prompt`들
(예: "자동 저장 기능 빼줘.")은 정보 누락 없이 명시화는 되지만 문장이 다소 기계적이다.

**제안**: PromptBuilder 마지막 단계에 선택적 LLM 재작성 단계를 추가하되, "확정된 정보" 목록을
grounding으로 강제해 LLM이 임의로 새 정보를 지어내지 않도록 제약. 결정론적 템플릿 출력은
LLM 실패 시 폴백으로 유지해 테스트 가능성을 잃지 않는다.

# 2026-08-19 추가 평가 (Groq/qwen3.6-27b, 30케이스 fixture) 기반 개선 후보

사용자가 직접 구축한 30케이스 평가 하네스(reference/omission/degree/comparison/scope 각 유형 +
compound/false_positive/false_negative/context_conflict/question_limit)를 Groq `qwen/qwen3.6-27b`로
실행한 결과: PASS 9, FAIL 12, REVIEW 2, ERROR 7. 아래는 원본 트랜스크립트를 케이스 단위로 직접
검토해서 찾은 근본 원인과, 위 1~4번과 구분되는 **새로운** 개선 후보다. 우선순위는 영향도 순.

## 5. [P0] Groq reasoning 모델의 "생각 폭주"로 인한 응답 절단 — ERROR 7건 중 6건의 공통 원인

**관찰**: ERROR로 분류된 7건 중 6건(O1, D1, D4, C1, M1, S4)의 원본 응답을 보면, 모델이
`<think>` 블록 안에서 같은 결론을 "Wait, let me reconsider...", "Actually..." 같은 자기수정을
반복하며 수천 단어 분량으로 사고를 이어가다가, `</think>` 종료 태그나 최종 JSON을 출력하기도
전에 응답이 그대로 끊긴다. C1은 심지어 최종 JSON을 쓰기 시작한 뒤 `"impact":` 에서 잘렸다
(`Unexpected end of JSON input`). 이건 이전에 고친 "think 블록이 섞여 나오는" 문제([test/llmClient.test.ts](../test/llmClient.test.ts))와 달리, **응답 자체가 끝까지 생성되지 못하고 잘리는** 별개의 실패
모드다.

**근본 원인**: [src/llm/groqClient.ts](../src/llm/groqClient.ts)가 `max_tokens`를 지정하지 않고
있고(Anthropic 클라이언트만 `max_tokens: 1500` 설정), reasoning 모델 특성상 사고 과정 자체가
매우 길어질 수 있어 기본/암묵적 완료 길이 한도에 먼저 도달해버린다.

**영향**: 30케이스 중 7건(23%)이 아예 결과를 못 냈다 — 이건 판단 품질 문제가 아니라 순수하게
인프라 설정 문제라서, 다른 어떤 프롬프트 튜닝보다 **고치기 쉽고 효과가 확실한 v1 최우선 항목**이다.

**제안**:
1. `GroqLLMClient`에 `max_tokens`(예: 4096 이상)를 명시적으로 설정해 최소한 잘리지 않게 한다.
2. Groq가 해당 모델에 대해 `reasoning_format: "hidden"`(또는 `"parsed"`) 파라미터를 지원하는지
   확인 — 지원한다면 사고 과정을 애초에 응답 채널에서 분리해 토큰 낭비와 파싱 위험을 근본적으로
   없앨 수 있다. `reasoning_effort` 파라미터로 사고 깊이 자체를 낮추는 것도 대안.
3. 위 두 조치로도 불안정하면, 이 워크로드(구조적 JSON 판단)에는 reasoning 모델보다
   非-reasoning 모델(예: 이전에 검증한 `openai/gpt-oss-120b`, 다만 [#8] 참고)이 더 적합할 수 있음 —
   "reasoning 모델 = 더 똑똑함"이 이 태스크에 항상 유리하지 않다는 근거가 이번에 확보됨.
4. `parseJsonResponse`가 파싱 실패 시 원본 응답이 아무리 길어도 전체를 에러 메시지에 그대로
   포함하는 중(현재 수만 자 분량 원본이 통째로 로그에 남음) — 실패 원인 파악용으로는 좋지만
   운영 시 로그 폭증 위험이 있어 앞부분 N자로 잘라 로깅하는 것도 함께 검토.

## 6. degree의 impact 과대평가: 명시적 강조가 없는데도 CLARIFICATION_REQUIRED로 감

**관찰**: [#1]에서 이미 지적한 문제의 재현이 이번에 3건 더 나왔다.
- **D2** "설명을 조금만 더 자세하게 써줘." (직전 대화에 지원동기 초안 존재) → 기대: SAFE_INFERENCE,
  질문 없음. 실제: "조금만 더"를 impact high로 판단해 "구체적인 기준이 있다면 알려주세요"라고 질문.
- **S3** "전체적으로 조금 더 자연스럽게 바꿔줘." → scope는 정확히 RESOLVED했지만 같은 문장의
  "조금 더"가 또 CLARIFICATION_REQUIRED.
- **R2**의 degree 부분("이 부분 조금 줄여줘"의 "조금")도 동일 패턴.

**근본 원인**: AmbiguityAnalyzer 시스템 프롬프트의 규칙 — "사용자가 글자수/분량 등 제한 준수를
강조했지만 실제 기준값이 문맥 어디에도 없다면 impact를 high로 표시하라" — 는 원래
"꼭 지켜줘", "반드시 지켜야 해" 같은 **명시적 강조가 있는 경우**를 위한 규칙인데, 모델이 이걸
"조금", "조금만 더" 같은 **일반적인 정도 부사 전체**에 과도하게 일반화해서 적용하고 있다.
즉 규칙 자체는 스펙대로지만, 모델이 "적용 조건(사용자의 명시적 강조)"과 "결과(impact high)"를
분리하지 못하고 결과만 기계적으로 재현하는 중.

**제안**: AmbiguityAnalyzer 프롬프트에 대조 예시를 추가해 조건을 명확히 분리한다.
- impact=high로 볼 것: "꼭", "반드시", "정확히", "~자 이내로 무조건" 등 **강제성 신호**가 함께 있는데
  실제 기준값이 없는 경우만.
- impact=low(SAFE_INFERENCE 기본값)로 볼 것: "조금", "좀 더", "자연스럽게", "적당히" 등 **강제성
  신호 없이 순수 정성적 스타일 조정**을 요청하는 경우 — 이게 D2, S3, R2, 그리고 처음 발견된
  degree-B 케이스([v0-manual-verification.md](./v0-manual-verification.md) Case A) 모두의 공통점.
회귀 테스트에 D2/S3를 그대로 추가해 이 구분이 실제로 적용됐는지 검증.

## 7. omission이 reference/scope/comparison으로 이미 해소된 대상을 중복으로 다시 질문

**관찰**: 4건에서 동일 패턴 확인.
- **C3** "앞에서 작성한 지원동기와 비슷한 문체로 성장과정을 작성해줘." → comparison은 정확히
  RESOLVED("앞서 작성한 지원동기 문단의 문체")했는데, 같은 문장의 "성장과정을 작성해줘"에 대해
  또 omission을 만들어 "성장과정을 작성해줘가 정확히 무엇을 가리키는지"를 질문. 그런데 "성장과정"은
  이미 문장에 명시된 대상이다 — 애초에 모호하지 않다.
- **FP1** "이 부분, 즉 결론 문단만 수정해줘." → reference/scope는 "결론 문단"으로 정확히
  RESOLVED했는데 "수정해줘"에 대해 또 omission이 발생해 "수정해줘가 무엇을 가리키는지" 질문.
  대상은 바로 앞에서 이미 확정됐다.
- **FP2** "앞에서 작성한 지원동기와 같은 구조로 성장과정을 작성해줘." → 심지어 "앞에서 작성한
  지원동기"라는, 문장 자체에 대상이 명시된 구절까지 reference로 잡아 별도 질문 생성.
- **S2** "이 부분만 수정해줘." (3개 섹션 검토 중) → scope 질문("기술 설명/시장 분석/기대 효과
  중 어디")과 omission 질문("수정해줘가 뭘 가리키는지, 후보도 동일한 3개 섹션")이 사실상 같은
  불확실성을 두 번 묻는다.

**근본 원인**: omission 판단이 문장 전체 맥락과 독립적으로 "해줘/바꿔줘/작성해줘" 같은 동사
어미만 보고 "대상이 생략됐는지"를 판단하고 있어서, 같은 문장 안에서 reference/scope/comparison이
이미 그 동사의 목적어를 확정했는지를 확인하지 않는다.

**제안**: AmbiguityAnalyzer 프롬프트에 명시적 순서 규칙 추가 — "먼저 문장 내에서
reference/scope/comparison으로 확정되거나 이미 명시적으로 언급된 대상이 있는지 확인하고,
그 대상이 이미 동사(해줘/바꿔줘/작성해줘 등)의 목적어 역할을 한다면 별도의 omission 항목을
만들지 마라." 이건 [#2]에서 남겨둔 "실제 발생 빈도 지켜보자"는 관찰을 넘어, 이번 데이터로
"단순 발생빈도 문제가 아니라 명확한 로직 누락"이라는 게 확인된 것 — 우선순위를 올려야 함.

## 8. 다중 턴 문맥에서 "가장 최근 화제" 우선순위가 반영되지 않음

**관찰**: **R2** "이 부분 조금 줄여줘." — 대화가 (지원동기 수정 → 지원동기 완료 → 성장과정
수정 시작 → 성장과정 완료) 순으로 4턴 진행된 뒤의 요청인데, 가장 최근 화제인 "성장과정"이 아니라
"성장과정"과 "지원동기" 둘 다를 동등한 후보로 제시하며 `context_support: medium`으로 질문했다.
직전 턴이 명백히 성장과정 작업이었는데도 우선순위를 안 줬다.

**근본 원인**: [contextResolver.ts](../src/contextResolver.ts)는 대화를 단순 시간순 텍스트로
포맷팅만 하고("단순한 최근성만 보지 말고 의미적 연결도 판단" — 원 스펙 5번), AmbiguityAnalyzer
프롬프트에도 "가장 최근 화제에 더 높은 context_support를 부여하라"는 명시적 지침이 없다.

**제안**: AmbiguityAnalyzer 프롬프트에 "여러 후보가 대화 여러 시점에서 나온다면, 가장 최근 1~2턴에
등장한 후보를 더 강한 문맥 근거(context_support)로 취급하라"는 규칙을 추가. 단, 스펙 5번이
"복잡한 scoring system은 만들지 않는다"고 명시했으므로 turn-weight 계산 알고리즘을 코드로 만들지
말고, 어디까지나 LLM 프롬프트 지침으로 유지 (v0 설계 원칙과 일치).

## 9. 문서 vs 최신 발화가 충돌할 때 우선순위 규칙이 없음

**관찰**: **CTX1** "그 기준으로 작성해줘." — 첨부 문서엔 "1,000자 이하", 그런데 바로 직전 사용자
발화가 "교수님이 **이번에는** 700자로 작성하라고 했어"(명백한 override 신호). 기대: 최신/명시적
발화(700자)가 우선해 RESOLVED. 실제: 두 값을 동등 후보로 놓고 질문.

**근본 원인**: [#8]과 같은 뿌리(최근성 미반영)이지만, 여기선 "문서 vs 대화"라는 **출처 간
우선순위** 문제이자 "이번에는" 같은 **명시적 override 표현**을 인식하지 못한 것까지 겹친 문제.
CTX2(두 문서 간 마감일 충돌, 8/30 vs 9/5)는 올바르게 CLARIFICATION_REQUIRED로 처리된 것과
대조하면, "같은 종류의 출처끼리 충돌"(CTX2, 정답)과 "구두 발화가 문서를 명시적으로 갱신"(CTX1,
오답)을 구분하지 못하는 것으로 보인다.

**제안**: AmbiguityAnalyzer 프롬프트에 "사용자의 가장 최근 발화가 첨부 문서의 내용을 대체/갱신하는
것으로 보이면(예: '이번에는', '이번 건', '다르게' 등 대비 표현 동반) 문서보다 최신 발화를
우선하라"는 규칙 추가. CTX1을 회귀 테스트로 고정.

## 10. reference vs comparison 경계가 모호함 ("전에 거" vs "전처럼")

**관찰**: **M4** "전에 거 기준으로 이 부분만 수정해줘." 기대 타입은 comparison(비교 기준)인데
실제로는 reference로 분류됨. 다만 후보(v1/v2)와 질문 내용 자체는 정확했다 — **라벨만 다르고
기능은 맞음**.

**해석**: "전에 거"(이전 산출물 그 자체를 가리킴)와 "전처럼"(이전 산출물의 스타일/기준을
따르라는 의미)은 원 스펙 예시에서 구분되지만, 둘 다 "전"이라는 같은 어근을 공유해 모델이
혼동하기 쉽다. 이건 판단 품질 문제라기보다 **타입 분류 경계 정의 문제**다.

**제안**: AmbiguityAnalyzer 프롬프트에 대조쌍 예시 추가 — "'전에 거', '그때 그거'처럼 이전
산출물 자체를 가리키면 reference, '전처럼', '~대로', '~같이'처럼 이전 산출물의 스타일/기준을
따르라는 의미면 comparison." 다만 최종 사용자 경험(질문 텍스트, 후보, 답변 처리)에는 영향이
없으므로 우선순위는 낮음 — type 라벨이 로깅/분석 목적 외에 실제 동작에 쓰이지 않는다면 생략 가능.

## 11. 부록 — 이번 평가에서 "FAIL"로 집계됐지만 실은 기능은 맞고 라벨만 다른 케이스들

O2, M4, FN2, S2 네 건은 모두 "탐지 누락: [기대 타입]이 탐지되지 않음"으로 FAIL 처리됐지만,
트랜스크립트를 직접 읽어보면 **질문 내용/후보/최종 판단은 실질적으로 타당**했고, type 라벨만
기대와 달랐다 ([#7], [#10] 참고). FN2는 평가 fixture의 `behavior` 설명 자체가 "omission 또는
reference 중 하나라도 탐지되면 충분"이라고 OR 조건을 명시했는데도, 자동 채점 로직은 두 타입의
집합이 정확히 일치해야 PASS로 판정한 것으로 보인다 — **이건 시스템 버그가 아니라 평가 하네스의
채점 로직이 자기 자신의 `behavior` 서술과 불일치하는 문제**다.

**제안**: v1에서 이 30케이스 fixture를 계속 회귀 테스트로 쓸 계획이라면, 채점 로직을 "type 정확히
일치"에서 "핵심 기능 지표(질문 여부, 질문 개수, 후보 내용, 최종 status) 우선 + type은 참고 정보"로
낮춰서, 실제로 고쳐야 할 로직 버그([#5]~[#9])와 라벨링 취향 차이를 분리해서 봐야 함.

## 12. zod 스키마 위반 시 재시도 없이 즉시 ERROR

**관찰**: **M3** "이거 보고 필요한 부분만 적당히 정리해줘." — 4개 모호성 중 하나가
`"impact": "medium"`을 반환해 zod가 `high|low` 위반으로 즉시 reject, 전체 요청이 ERROR로 끝남
(3개는 정상 판단이었을 수도 있는데 통째로 버려짐).

**근본 원인**: [ambiguityAnalyzer.ts](../src/ambiguityAnalyzer.ts)의 `ResponseSchema.parse()`가
실패 시 바로 예외를 던지고, [workflow.ts](../src/workflow.ts)에는 재시도 로직이 없다.

**제안**: 스키마 검증 실패 시 1회에 한해 "이전 응답이 형식을 위반했습니다: {에러 내용}. impact는
반드시 high 또는 low 중 하나여야 합니다." 같은 교정 메시지를 덧붙여 재호출하는 self-repair 루프
추가. 재시도도 실패하면 현재처럼 ERROR로 반환(무한 재시도 금지 — v0/v1 모두 "과도한 복잡성
지양" 원칙과 균형).
